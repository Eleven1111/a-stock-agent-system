# 已证伪方案台账

本文件只记录**试过并且失败了的方案**，以及失败的证明方式。目的是让后来的改动不必
重新付一遍同样的代价。

动机来自一个可观察的事实：这些结论此前全部埋在 PR 正文和 issue 评论里。它们从未
丢失，但也从未被读到 —— 提方案的人不会去翻三个月前某个 PR 的描述。

## 台账规则

- **只进不出。** 条目不删除、不改写结论。方案后来被新证据推翻，就追加一条新条目并
  在旧条目上注明「已被 F0NN 更新」，而不是修改旧条目。代码可以回滚，台账不回滚。
- **准入门槛是「试过且失败了」，不是「觉得不好」。** 每条必须给出可核对的证伪方式：
  具体数字、失败的测试数、可复现的命令，或者代码里的确切位置。没有实证的判断不进
  台账。
- **每条必须回答「别再试什么」。** 只说「A 方案不行」没有价值；要说清楚下次有人产生
  同样念头时，应该被什么拦住。
- **只写可公开的工程事实。** 持仓、生产数据、策略 edge 的推理过程不进本文件。

## 本文件只进提案路径，不进执行路径

**读者是「要改动这个系统的人」，不是「正在跑的作业」。**

- ✅ 提案与评审：`AGENTS.md` 的 Change Protocol、PR 评审、设计讨论。
- ❌ 执行：专家 profile（`config/*.json` 的 `profile` 路径与
  `skills/research-committee/experts/*.md`）、`skills/*/SKILL.md`、
  `cron/hermes-cron-manifest.json`、evidence pack。

把它接进执行侧看起来是「让 agent 更懂事」，实际有害，两条独立理由：

1. **实测会掉分。** WikiSkill (arXiv:2608.27454) Table 3 做了这个消融：让提案方读知识库
   是 48.7 → 63.7（+15.0），但**再让执行方也读，反而 63.7 → 60.9**。原因是执行方会绕过
   既有流程、直接用知识库里的结论作答，于是产生的轨迹对改进流程不再有信息量 ——
   知识库反而堵死了它自己的更新来源。
2. **本仓库的上下文预算。** 执行侧上下文膨胀是已知问题（`AGENTS.md` 有 140 行硬预算、
   evidence pack 有硬字符预算、artifact 早已改为只存引用）。本文件只增不减，接进执行侧
   等于给每次作业挂一个无上界的负担。

`expert_runner._profile_text()` 会把 `profile` 指向的**整个文件**注入专家轮次，
因此在 `config/*.json` 里把 `profile` 指向本文件是最容易发生的一种接错。
`tests/test_repository_governance.py` 有一条测试守着上述执行侧入口不出现本文件的引用。

## F001 · 东财行业映射刷新作业从未成功过

- **结论**：`industry-map` 刷新作业上线起从未产出过正确结果，但它一直在被调度、也一直
  没有报警，因此长期被当作「已经在跑」。
- **证伪方式**：排查刷新链路时发现该作业自上线以来零成功产出；修复提交的标题即
  「修复刷新作业**从未成功过**的缺陷」。
- **别再试**：不要从「作业已注册、进程在跑、缓存文件存在」推断产出正确。判据必须是
  产出内容本身被校验过。另见 F004 —— 同一类错误的字段级版本。
- **现状**：已换成新浪 + 证监会源（#156），覆盖率后续在 #161 提到 94%。缓存口径**不是**
  申万一级，消费方不要按申万一级理解。

## F002 · 公告贝叶斯评分不能用于 Top-N 选股

- **结论**：该评分体系可以做**分流**（把每日约 1450 条公告压到约 165 条可深读集合），
  但不能产出排序名单。
- **证伪方式**：2026-07-31 / 08-01 双日全量实测。
  - **Top-N 无唯一解**：08-01 去重后 501 只个股，Top20 的分数门槛是 7 分，而并列 7 分的
    有 **45 只**。取哪 20 只取决于接口返回顺序，不取决于分数。分数是整数，1296 条有效
    评分只落在 **16 个取值**上。
  - **双评分实质是单评分**：anchored 模式下 `bayes == nss` 占 68.0%（07-31）/ 69.1%（08-01）。
    内置参数是从公开结果反推的锚定值，不是原始 MCMC 后验。
  - **92% 命中率掩盖漏网结构**：未命中的 8% 是「核电项目核准」「德国 GMP 证书」
    「一致行动协议」这类高价值非常规事件 —— 常规公告好命中，有 alpha 的漏。
- **别再试**：不要用低基数整数分构造排序名单。判断一个分数能否排序，先统计**目标名次
  上的并列样本数**；并列数远大于名额数时，排序结果由数据源顺序决定，不由分数决定。
- **现状**：定位固定为分流器（#158），不产出排序名单，不产出买卖建议。

## F003 · `skills/common` 不能迁成绝对包导入

- **结论**：把 `skills/common` 内部改成 `from skills.common.X import Y` 的真包化方案，
  实测不可行。
- **证伪方式**：把内部 237 处改成绝对包导入后 **50 个测试失败**，全部同因 —— 同一份源码
  被加载成两个模块对象（平铺 `http_client` 与 `skills.common.http_client`），产生两套类
  对象，导致 `except DataSourceError` 与 `isinstance` 跨边界失效。已实测确认这两个对象
  本来就不是同一个。
- **别再试**：不要做「迁一半」的包化。中间态**严格劣于两个端态**。整张图一次性迁移的
  规模是 237（内部导入）+ 约 100（消费方）+ 99（测试，其中 55 个用
  `spec_from_file_location` 按路径加载）≈ **300+ 文件**，需要作为独立项目立项，不能顺带做。
- **另有一条相关约束**：判断某个模块能否搬走，只用 AST 扫 `import` 语句会漏。
  `chan_structure` 通过动态加载依赖 4 个兄弟模块、后者再动态依赖 2 个，真实闭包是静态
  判断的 3.5 倍。出方案前必须另外 grep `importlib.import_module` /
  `spec_from_file_location` / `__import__`。
- **现状**：取安全的那一半 —— 平铺名保持唯一规范名，路径引导由 `skills/common/__init__.py`
  自持（#193 / #194）。

## F004 · 竞价门控读的 `book_quality` 没有任何生产写入方

- **结论**：#312 引入的 MFI 过热竞价门控，判据字段与采集器实际写出的字段对不上，因此
  门控从上线起就没有按文档描述的语义运行过。
- **证伪方式**：全仓 grep `book_quality`，除门控自身的读取处外，只出现在两条测试
  fixture 里 —— 零生产写入方。采集器实际写出的是 `book_coverage_status`
  （`available`/`missing`/`not_supported`）与 `auction_book_status`
  （`ok`/`stale_last_good`/`unavailable`）。
- **后果**：`book_quality != "ok"` 恒真，`overheated` / `terminal_acceleration` /
  `bearish_divergence` 三档候选无论五档质量如何一律被拒；`stale_last_good` 判据读的
  `book_status` 同样对不上，永不触发。方向是 fail-closed，未放行不该放行的候选，但
  文档描述的门控语义从未运行。
- **为什么测试没拦住**：守它的测试 fixture 自己伪造了 `book_quality: "ok"` 和
  `book_status: "fresh"` —— 后者甚至不是采集器会产出的取值。**断言的是没有生产写入方的
  字段**，因此恒绿。
- **别再试**：不要用配置断言或字段值断言代替行为断言。门控类守卫必须做**契约测试**：
  把生产者真实产出直接喂进消费者，任一侧字段改名或错位即失败。
- **现状**：已接到真实字段并补契约测试（#313）。别名表与原委保留在
  `skills/common/candidate_pipeline.py` 的注释里。

## F005 · 09:35 撤单增加硬拒当前恒不触发

- **结论**：`_overheat_execution_rejections` 的「撤单增加 ≥ 30% → 拒绝追高」判定逻辑与
  测试都在位，但它读的 `order_cancel_increase_pct`（含 `cancel_rate_increase_pct` 等四个
  别名）**没有任何 provider 写入**，因此在生产中恒不触发。不要将其视为已生效的保护。
- **为什么免费 L1 补不上**（三条都是硬约束，不是缺代码）：
  1. `_reconstruct_quote_at_cutoff` 主动清空 `bids`/`asks`。这是 point-in-time 纪律 ——
     抓取时刻的盘口是「现在」，保留会造成未来数据泄露。
  2. 09:30–09:35 没有任何盘口采样作业（`open-confirmation` 的 cron 是 `35 9 * * 1-5`，单次）。
  3. **连续交易阶段委买减少 ≠ 撤单**：成交同样消耗委买，L1 五档快照区分不了「被吃掉」
     与「被撤掉」。区分需要逐笔委托（L2）。
- **别再试**：不要对连续交易阶段的五档序列算委买衰减然后称之为「撤单率」。A 股 09:20 后
  委托不可撤单，因此唯一干净的撤单观测窗口是 **09:15–09:20**。
- **现状**：#316 已实现 09:15–09:20 撤单窗口影子指标，带 `real_sample_count` /
  `real_minutes` / `provenance`，并有测试确保它**不**喂给 09:35 硬拒。09:35 硬拒本身仍然
  恒不触发，跟踪在 #314。阈值 30% 无回测依据。

## F006 · issue #311 描述的 MFI 门控在当时并不存在

- **结论**：issue #311 正文称 `mfi_overheat_gate`（policy `mfi-overheat-gate-v1`）已经能
  识别三档过热并施加线性扣分，并给出了四处代码位置。该前提不成立。
- **证伪方式**：`git log -S` 对 `assess_mfi_overheat` 与 `mfi_overheat_gate` 两个符号在
  **全部 git 历史**中均零命中；正文引用的四处位置对应的是其它代码。当时的真实状态是
  MFI 只作为 `observable_proxies` 展示，不进任何评分与门禁。
- **影响**：「把线性扣分改成非线性」实际是从零建门控，而不是修改既有函数 —— 改动的性质
  与范围完全不同。若按正文基线复查，会得出错误的验收结论。
- **别再试**：不要按 issue / 事故报告正文的位置描述直接动手。正文里的「已实现」「疑似」
  「脚本保留在 X」都要先核实：符号用 `git log -S` 查历史，声称存在的产物要在仓库里找到。
  一条推测若不复现，建立在它之上的整个方案的谓词可能永不触发 —— 修了等于没修。

## F007 · 「存在第二套超时机制」是时点错配造出来的幻觉

- **结论**：排查 #321 时，观察到一批 `status=timeout` 的运行**远未到配置的上限**
  就被判超时，且超时点是方差近乎为零的整数（30 / 45 / 120 / 420 / 600 秒），据此推断
  「除 manifest 的 `run.timeout_seconds` 外另有一套超时机制」。该推断不成立。
- **证伪方式**：把 `cron/hermes-cron-manifest.json` 回滚到那批运行发生的时点再比对：

  | job | 运行时（07-27）上限 | 07-31 起 | 今天 | 观测到的超时点 |
  | --- | --- | --- | --- | --- |
  | candidate-discovery | **420** | 1500 | 2400 | 420 |
  | capital-flow | **120** | 300 | 300 | 120 |
  | industry-map-refresh | **120** | 600 | 1800 | 120 |
  | open-confirmation | **45** | 180 | 180 | 45 |
  | auction-finalize | **30** | 180 | 180 | 30 |

  每一个"异常"超时点都**正是当时生效的上限**，且全部在 07-31 被上调。287 条超时
  全部是普通的 job 级超时，不存在第二套机制。
- **根因**：把 2026-07-27..08-07 的运行数据，与 2026-09-01 的配置做了对照。这是一次
  时点错配的 join。仓库对行情证据有严格的 PIT 纪律，**但同一条纪律同样适用于配置**：
  分析历史运行时，配置也必须取运行发生那一刻的版本。
- **别再试**：不要拿历史运行数据去比对当前配置。任何「历史运行 × 配置」的分析，
  第一步是 `git rev-list -1 --before=<运行日期> -- <配置文件>` 把配置回滚到时点。
- **提前识别的信号**：**方差近乎为零的整数阈值，是"某处配了个常量"的特征，不是
  "存在未知机制"的证据。** 当这个常量对不上当前配置时，先怀疑配置变过，而不是先
  假设有隐藏机制 —— 后者会凭空造出一个不存在的系统，并让基于它的整个排查方向作废。
- **现状**：#321 里已记录该推断被证伪的过程，避免后来者重走。真正未解决的是
  `news-monitor-intraday`（上限 240s 自始未变，成功中位 17s、失败卡满 240s）。
