## 0. 总览：七个问题不是并列的

先看依赖关系，再定顺序——这决定了为什么不能按反馈顺序逐个修：

```text
#1 数据源稳定性 ────────── 一切的地基，数据不稳则下游全部失真
      │
      ├─→ #2 新闻/政策捕获 ──→ 主题体系的事件输入
      │
      ├─→ #4 板块/主题体系 ──┬→ #3 候选链路的"主题健康度"门禁输入
      │                      ├→ #7 打板反转的主要归因维度（fading 主题追高）
      │                      └→ 弱市强势主题捕捉
      │
      ├─→ #3 候选流转状态机 ──→ #6 serenity 的需求来源（复核拉动深研）
      │
      └─→ #7 策略归因 ──→ #5 chanlun 定位（第二策略需要结构过滤器和回测门控）
```

| # | 问题 | 根因类别 | 阶段 |
|---|---|---|---|
| 1 | 数据源不稳、东财常挂 | 基础设施缺仲裁层 | **P0** |
| 7a | 打板次日反转（归因部分） | 先量化确认再动策略 | **P0** |
| 3 | 筛选→观察→候选→复核不稳 | 流转缺显式状态机 | **P1** |
| 6 | serenity 使用率低 | 缺稳定的执行入口与需求牵引 | **P1** |
| 4 | 板块/主题监控太粗 | 缺动态主题层与相对强度视角 | **P2** |
| 2 | 新闻/政策捕获不及时 | 轮询架构 + 单一搜索源 | **P2** |
| 7b | 第二套策略 | 依赖 #4 主题数据 + 回测门控 | **P3** |
| 5 | chanlun 空转 | 定位未落定 | **P3**（评估在 P0 就做） |

## 1. 数据源稳定性（P0）

### 诊断

现状：`provider_contract.py` 提供了产品级 fallback 的结果契约，`provider_doctor.py`
有健康探针，`docs/eastmoney-resilience.md` 记录了东财专项加固——但这些是
**点状防御**。缺的是一个横切层：没有按"源×端点"的持续健康评分，没有熔断
（东财挂了之后每个消费者还在各自超时重试），没有多源同字段的自动仲裁，
覆盖缺口（某些数据只有东财有）没有系统清单。

### 方案

**1a. Provider SLO 账本 + 熔断器**（`skills/common/provider_health.py` 新增）

- 每次请求结果（成功/失败/延迟）落一条滚动窗口记录（复用 http_client 的
  出口统一拦截，不改业务代码）；
- 按 (provider, endpoint_class) 计算滚动成功率；跌破阈值 → 熔断打开，
  该源该类请求在冷却期内直接走 fallback，不再消耗超时时间——这是"东财
  挂了拖慢全链路"的直接解法；
- 健康评分写入 artifact，`provider-health` cron job（已存在）扩展为读这个账本。

**1b. 字段级多源仲裁**（`skills/common/field_arbiter.py` 新增）

- 为核心数据类型定义 canonical 字段 schema：行情快照、资金流、板块成分、
  涨停梯队；
- 每个字段声明有序源链（如 资金流: eastmoney → tencent → 缺失降级），
  仲裁器按源链取第一个健康源；
- **双源一致性抽检**：每天对少量样本用两个源取同一字段，偏差超阈值 →
  `quality_flag=cross_source_mismatch` 进快照，下游 fail-closed 机制自动生效。

**1c. 覆盖缺口清单与补源**

- 先跑一次盘点：哪些字段是"东财独家"（无 fallback）——这些是真正的脆弱点；
- 补源优先级：交易所官方文件（SSE/SZSE 日度数据，最稳但 T+1）→ akshare 备用
  端点 → baostock（EOD）→ 付费源（Tushare Pro）作为最后兜底，token 走 env；
- 慢变数据（行业映射、成分股）一律缓存优先 + 定时刷新（industry_map 已是
  此模式，推广到板块成分）。

### 验收

- 东财人为断网测试：全链路无 job 超时失败，仲裁自动切源，artifact 记录降级；
- provider-health 日报出现按源成功率曲线；东财独家字段清单归零或有明确兜底。

### 模型分配

**运行时零模型**（纯确定性代码）。实现由 **Claude Sonnet 5** 完成（结构化
工程任务，量大但模式清晰），架构评审用 Opus 4.8 过一遍熔断阈值设计。

## 2. 新闻与政策捕获（P2）

### 诊断

现状：`news_monitor_v3` + `official-policy-watch`（10 分钟轮询）+
`policy-intent-decoder`，新闻搜索依赖 SerpAPI。问题：轮询有固有延迟；
SerpAPI 是单点且按 query 计费，"搜出来"的新闻天然滞后于"推送出来"的新闻；
重大消息与日常噪声走同一条管道，没有旁路。

### 方案

**2a. 采集升级：从"搜"到"订"**

- 一手源直连清单（RSS/HTML 轮询，零 API 费）：国务院/发改委/证监会/央行
  发布页、新华社/人民日报要闻、cninfo 公告流、交易所监管动态；
- `agent-reach` 类多平台抓取可作为补充源（雪球/微博热点），标记为二手，
  只做情绪证据不做事实源；
- 全部进统一去重（novelty_gate 已有内容指纹机制，直接复用）。

**2b. 两级流水线：规则粗筛 → 模型分级**

```text
L1（确定性，每 5-10 分钟）：关键词/来源位阶/正则规则粗筛
    → 90% 噪声在这里出局，零 token
L2（模型，仅对 L1 通过项）：结构化分级输出
    → materiality 0-3 / 影响板块 / 时效窗口 / 是否需要深解读
```

**2c. 重大事件旁路（breaking path）**

- L2 判定 materiality=3 → 不等收盘调度：立即入队 research task
  （`anomaly_review` 或新增 `event_review` 类型）+ 走 delivery 推送；
- `realtime_catalyst_trigger`（已存在）接到这条旁路上，实现"盘中重大消息
  → 半小时内有委员会结论"。

**2d. 政策深解读按需触发**

- policy-intent-decoder 输出的高位阶政策（多部委/硬工具）自动入队
  `user_request` 级研究任务，让委员会评估传导链——政策支持从"解码一次"
  变成"解码 + 委员会复核"两级。

### 验收

- 重大政策从发布到系统产出结构化解读的延迟 < 30 分钟（现状：最长一个轮询
  周期 + 收盘调度）；
- SerpAPI 调用量下降（被 RSS 直连替代），月度新闻覆盖率抽检上升。

### 模型分配

- **L2 批量分级：Claude Sonnet 5**——高频、廉价、结构化输出稳定，这是每天
  几十次的调用，成本敏感；
- **重大政策深解读（materiality=3）：Claude Opus 4.8**——低频高杠杆，政策
  意图与传导链推理是全系统对推理深度要求最高的场景之一；
- **可选：GPT 5.5 做分歧仲裁**——当 Sonnet 分级结果落在 2/3 边界时用不同
  厂商模型复判一次，跨厂商误差去相关，避免同源盲点漏掉大事。

## 3. 候选流转链路加固（P1）

### 诊断

现状：`candidate_lifecycle.py` 已有按日持久化的生命周期记录，
`funnel_recall_report` 能统计漏斗，但"筛选→观察→候选→复核"的**迁移规则
散落在各脚本里**——candidate_discovery、closing-triage、open_confirmation
各自判断各自写，没有一个模块拥有"状态迁移"的唯一裁判权，这就是"不稳"的
根源：同一只票可能被不同 job 以不同理由推进或丢弃，且原因不可追溯。

### 方案

**3a. 显式状态机收权**（`skills/common/candidate_fsm.py` 新增）

```text
screened（入筛）→ watching（观察）→ candidate（候选）→ confirmed（复核通过）
                                                      ↘ dropped（淘汰，带原因码）
```

- 所有状态迁移必须经过 `candidate_fsm.transition(code, to_state, reason_code,
  evidence_ref)` 唯一入口，直接写 lifecycle 记录 + 迁移事件；
- 每个迁移定义 guard（前置状态 + 数据条件 + 冷却），guard 不满足 → 拒绝迁移
  并记录，**杜绝各脚本绕过状态机直接造候选**；
- 迁移原因码枚举化（`score_above_threshold` / `theme_fading` /
  `research_rejected` / `stale_data_timeout`...），funnel 报表按码统计流失。

**3b. 复核环节接研究委员会（闭环已就绪）**

- `candidate → confirmed` 的迁移 guard 增加一条：该标的当日
  `candidate_deep_dive` 任务的 verdict 不得为 `rejected`；
- verdict=rejected → 状态机自动降级回 watching（原因码 `research_rejected`）；
- verdict=disputed → 保持 candidate 不升级，等次日证据（分歧即暂缓）。

**3c. 超时与退化规则**

- watching 超过 N 日无新证据 → 自动 dropped（`stale_watch`），防观察池膨胀；
- confirmed 但连续 M 日未成交 → 回退 candidate，防"僵尸确认"。

### 验收

- 任意一只票的完整流转历史可用一条命令回放（状态+时间+原因码+证据引用）；
- funnel 报表出现按原因码分解的各级流失；无任何脚本再直接写候选状态。

### 模型分配

状态机与 guard **纯确定性代码，运行时零模型**，实现 **Claude Sonnet 5**。
复核环节即研究委员会现有分工（见 §8 总表）。

## 4. 板块/主题动态监控（P2，工程量最大）

### 诊断

现状：`sector_taxonomy.py` 已明确"industry（稳定分类）≠ sector（可交易主题）"
并阻止大行业标签冒充主题——方向对，但只做了"防守"（不让粗标签进来），
没做"进攻"（主动发现和跟踪细主题）。`market_temperature` 是全市场单一温度，
弱市里"全场冷但某主题热"的结构性信号被平均掉了——这正是反馈 #4 的核心。

### 方案

**4a. 三层主题体系**（`skills/common/theme_registry.py` 新增）

```text
L1 行业（现有，稳定，用于风控集中度）
L2 概念板块（东财/同花顺概念指数成分，日度同步，缓存优先）
L3 动态主题（生成式：涨停共性 + 新闻聚类 + 政策指向，有生命周期，可消亡）
```

L3 主题是注册制：每个主题有 id、成分股、起始日、来源证据、状态——和
monitor_registry 的墓碑机制同构，消亡主题不复活。

**4b. 主题强度日评（确定性）**

每日对每个活跃主题计算并落 artifact：

- **广度**：成分涨停数、上涨占比、连板梯队高度（复用 market_temperature 的
  ladder 逻辑，按主题分组）；
- **资金**：成分主力净流入聚合（东财资金流经 §1 仲裁层取）；
- **相对强度 RS**：主题等权收益 − 全 A 中位收益，5/10/20 日滚动——**弱市抓
  强势的关键就是 RS 而非绝对涨幅**，全场跌 2% 里跌 0.2% 的主题就是强主题；
- **持续性**：强度连续天数、断板后修复速度。

**4c. 主题生命周期状态机**

```text
emerging（首次共振）→ mainline（主升，梯队完整+RS 领先）
  → diverging（分歧，高位断板/成分分化）→ fading（退潮）
```

- 判定规则全部确定性（梯队高度变化、promotion_rate、RS 拐头）；
- **候选加分/降权接入**：mainline 主题成分加分，diverging/fading 主题的
  打板候选自动降权——这直接回应 #7 的部分成因（追了退潮主题的板）；
- 强主题自动生成 theme monitor + 触发新任务类型 `theme_review`（委员会
  评估主题驱动逻辑与持续空间）。

### 验收

- 弱市日（温度 < 阈值）系统仍能输出 RS 排名前 3 的主题及其龙头结构；
- 回看近 60 日：fading 判定滞后不超过 2 个交易日（用历史数据回放校验）；
- 候选池中标注主题阶段，`theme_stage` 出现在证据包里。

### 模型分配

- 强度/RS/生命周期计算：**零模型**（确定性），实现 **Claude Sonnet 5**；
- L3 主题聚类与命名（每日一次，把涨停共性+新闻线索归纳成"主题"）：
  **Claude Sonnet 5**——归纳命名任务，量少但每天都有；
- `theme_review`（mainline 主题的驱动逻辑深研，低频）：**Claude Opus 4.8**；
- 主题判定规则的历史回放校验报告：代码产出，**GPT 5.5** 做一次独立复核
  （检查判定规则是否有前视偏差——跨厂商红队）。

## 5. chanlun 定位落定（评估 P0 做，集成 P3 做）

### 诊断

chanlun-backtest 是研究门控框架（IS/OOS、置换检验、FDR），`research_evidence`
桥接进 policy——机制健全，但**没有策略真正走完门控注册**，于是它成了
"有裁判无比赛"的空转设施。

### 方案（先评估，二选一落定）

**5a. 一次性评估（P0 就做，成本低）**：选 1-2 条最简缠论规则（如"三买点
回踩确认"），用现有回测框架完整跑 IS/OOS + 统计检验，出一份评估报告。

**结果 A——通过门控**：注册进 strategy_registry，允许影响 live 排序，chanlun
从空转变成第二策略（§7b）的信号源之一。

**结果 B——不通过**：chanlun 降格为**结构位置过滤器**，不再作为独立信号：

- 在证据包新增 `structure_position` section：当前价格处于笔/线段的什么位置、
  是否背驰——供 risk_redteam 引用（"线段末端背驰"→ risk_flag，降低追高）；
- 明确写入文档"chanlun 仅作位置证据，不预测方向"，停掉与此无关的维护。

两个结果都比现状好：**要么上场，要么当边裁，不再空转**。

### 模型分配

- 回测执行：确定性代码；
- 评估报告解读与定位决策建议：**Claude Opus 4.8** 一次性（统计结果的严谨
  解读，质量关键、频率极低）。

## 6. Serenity 深研激活（P1，改造成本最低）

### 诊断

`serenity_refresh_queue` 的设计（调度器判 due → agent claim → 执行 → 回流
deep_research_cache）是对的，使用率低的原因和研究委员会上线前一模一样：
**没有稳定的模型轮次入口去消费队列**——队列在积压，没人干活。此外深研
缺少"需求牵引"：它按日程刷新，而不是被研究任务拉动。

### 方案

**6a. 队列合并进 research bus**

- 把 serenity 刷新做成研究任务的一种：`kind=serenity_refresh`，单角色
  `deep_researcher`，profile 指向 serenity skill 的执行入口；
- serenity_refresh_queue 的 plan 逻辑保留（它决定"谁 due"），但产出改为向
  research bus 入队——**一套队列、一套租约、一套预算、一个研究窗口**，
  消除两套并行队列的认知负担；
- 研究窗口的循环自然会消费它：`expert_runner next` 领到 serenity 工单 →
  执行深研 → scorecard 回流 deep_research_cache（complete 的 fail-closed
  校验保留：没有新缓存不算完成）。

**6b. 需求牵引：深研被复核拉动**

- `candidate_deep_dive` 构建证据包时发现 `deep_research` section 缺失或
  stale → 自动入队一个 `serenity_refresh`（优先级继承任务），并在本次
  finding 里如实标记"深度面证据缺失"；
- 效果：深研频率自动跟随候选热度——热门候选总有新鲜深研，冷门票不浪费。

**6c. 覆盖率可见**

- 周报加一个指标：候选池 top10 的 fresh 深研覆盖率——这个数字就是"serenity
  有没有起作用"的直接答案。

### 验收

- 部署一周后：top10 候选深研覆盖率 ≥ 80%；four_dim 深度分中来自真实深研
  （非 PE 兜底）的占比显著上升。

### 模型分配

**serenity 深研执行：Claude Opus 4.8，全系统最不该省的一笔 token**——供应链
拆解、财务质量、估值情景是最重的长链推理，深研一次、日评复用的缓存结构
决定了它天然低频，贵得起。scorecard 结构化回流已有校验，无需担心格式漂移。

## 7. 打板反转与第二策略（P0 归因 + P3 落地）

### 诊断

"当天涨势好、次日反转"在 T+1 制度下是致命的：打板赚的本质是**次日惯性溢价**，
当前数据说明这个溢价为负或不稳。可能的原因（需要数据确认，不要拍脑袋改
策略）：追入时主题已到 diverging/fading 阶段；高位板拥挤（crowding_fragility
的信号被忽略）；弱市环境下整体溢价失效；或入场模式本身（追涨停 vs 低吸）。

### 方案

**7a. 先归因，后动手（P0，纯统计，立即可做）**

新增 `scripts/strategy_attribution_report.py`：对历史打板信号按四个维度分层
统计 T+1 竞价溢价与 T+3 结算：

```text
维度1: 市场温度分层（强/中/弱市）
维度2: 主题阶段分层（emerging/mainline/diverging/fading — §4 落地前先用
        连板梯队高度近似）
维度3: 板位分层（首板/二板/三板+）
维度4: 入场模式分层（回封 vs 弱转强 vs 追板）
```

**改策略的依据必须来自这张表**，比如若数据显示"弱市 + 三板以上溢价全面为负"
——那答案是门禁而不是弃用。

**7b. 打板策略的三个候选调整**（按归因结果选用，不全上）

1. **环境门禁**：市场温度 + 主题阶段双条件不满足 → 打板信号只入 ledger 做
   research-only，不进推荐面（weak_market_delivery 已有该机制，扩展条件）；
2. **入场前移**：提高"竞价弱转强/首板回封低吸"权重、降低追板权重——
   低吸模式的次日容错远大于板上入场；
3. **退出改造**：从"持有等趋势"改为**T+1 竞价溢价套利**——竞价溢价达标
   （如 +3%）即挂卖出计划，不达标按既有 exit_signals 走止损。`exit_signals`
   已有 7 类信号框架，新增 `auction_premium_exit` 一类即可。

**7c. 第二套策略：主题主升回调（P3，与打板低相关）**

- 逻辑：§4 的主题体系判定 mainline 阶段 → 主题内龙头（非最高板，第二梯队
  质地股）5-10 日回调至支撑 + RS 保持领先 → 介入，持有 3-10 天；
- 与打板的相关性天然低：打板吃情绪日内动量（T+1 卖），回调策略吃趋势延续
  （周级持有）——组合层面平滑收益曲线；
- **必须走 chanlun-backtest 门控**（正好让 §5 的裁判有比赛可吹）：IS/OOS 不
  通过不进 live，这是 AGENTS.md 的既有铁律；
- chanlun 结构位置（若 §5 落定为过滤器）作为回调买点的位置证据。

### 验收

- 7a 报告产出且每月自动更新（挂 performance-weekly 后）；
- 调整后打板信号 T+1 竞价溢价中位数转正，或 research-only 拦截率与避损
  金额可量化；
- 第二策略 OOS 报告通过门控后才出现在 strategy_registry。

### 模型分配

- 归因统计：确定性代码（**Claude Sonnet 5** 实现）；
- **策略假设设计与调整决策建议：Claude Opus 4.8**——这是"用统计结果推导
  策略修改"的关键推理，也是全方案里最需要避免过拟合直觉的地方；
- **策略设计红队：GPT 5.5**——对 Opus 提出的策略修改做独立攻击（前视偏差、
  幸存者偏差、样本量陷阱），跨厂商去相关审查，结论分歧时以保守方为准；
- 回测与门控：确定性代码。

## 8. 模型分配总表与原则

### 分配三原则

1. **确定性优先**：能写成代码的绝不用模型——七个问题里约 70% 的工作量
   （仲裁层、状态机、主题强度、归因统计）运行时零 token；
2. **频率 × 杠杆定档**：高频结构化 → Sonnet 5；低频高杠杆 → Opus 4.8；
3. **跨厂商去相关**：凡是"复核/红队/第二意见"位置，刻意用与原判不同厂商

## 10. 与既有架构的关系（不变的东西）

本方案全部改造遵守既有铁律，无一例外：

- 事实平面确定性、快照不可变、signal ledger 唯一账本；
- 所有方向性输出过 decision policy，新策略过 OOS 门控才能 live；
- 研究平面只读证据包、只写自己的 data 区、产出永远是 gated proposal；
- 状态外置 `A_STOCK_STATE_HOME`，双运行时租约互斥；
- 缺数据 fail-closed，绝不把数据缺失解读为"没有风险"。

七个问题的修复没有一个需要突破这些约束——需要突破约束的方案就是错的方案。
